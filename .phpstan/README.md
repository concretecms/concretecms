# PHPStan

This directory contains everything needed to run [PHPStan](https://phpstan.org) on the Concrete CMS code base.
It's a separate Composer project, so that the dependencies of Concrete are not affected (PHPStan requires PHP 7.4+, Concrete supports PHP 7.3+).

## Usage

Install the dependencies (once):

```sh
composer install                          # in the root directory of the project
composer install --working-dir=.phpstan   # PHPStan and its extensions
```

Then, in this directory:

| Command                          | Description                                                                                      |
|----------------------------------|--------------------------------------------------------------------------------------------------|
| `composer run generate-stubs`    | Generate the stubs describing the methods handled by `__call`/`__callStatic` (see below)         |
| `composer run phpstan`           | Run PHPStan (additional PHPStan options can be passed after `--`, for example `-- --no-progress`) |
| `composer run generate-baseline` | Regenerate `baseline.neon` (see below)                                                           |

The stubs must be generated before running PHPStan (and regenerated when the facades or the permission keys change).

Always run PHPStan from this directory: the result cache (in the `tmp` directory) stores paths relative to the current working directory.

## Files

- `phpstan.neon.dist`: the PHPStan configuration (the specific settings are explained by the comments in the file itself).
  Create a `phpstan.neon` file (ignored by git) including it if you need local overrides.
- `bootstrap.php`: boots the Concrete environment (constants, autoloaders, class aliases, ...) without processing any request.
  PHPStan runs from a `.phar` file, and Concrete unregisters the `phar` stream wrapper: the bootstrap file restores it, even if Concrete fails to boot (so that the actual error is reported).
- `object-manager.php`: lets [phpstan-doctrine](https://github.com/phpstan/phpstan-doctrine) know the entity metadata (magic `findBy*`/`findOneBy*` repository methods, entity fields, ...) by providing the Doctrine EntityManager of Concrete.
  If the database is not configured (for example in the CI), it configures a fake connection that is never actually used (Doctrine only needs to know the platform, given by `serverVersion`).
- `baseline.neon`: generated by PHPStan, it lists the errors detected in the current code base.
  They are ignored, so that the CI only fails when new errors are introduced.
  Regenerate it when some of them are fixed, or when the PHPStan configuration/version changes.

## Stubs

The facades (`Core`, `Config`, `Database`, ...) and `Concrete\Core\Permission\Checker` handle their methods with `__callStatic`/`__call`, so PHPStan can't know them.
The `c5:ide-symbols phpstan` command generates `concrete/src/Support/__PHPSTAN_STUBS__.php` (ignored by git) describing those methods with `@method` annotations: it's used as a [stub file](https://phpstan.org/user-guide/stub-files).

PHPStan validates the stub files in isolation (it only knows the classes declared in the stub files and the PHP built-in ones), so the generated file also contains empty declarations of every class it references, except the ones already declared by the stubs of phpstan-doctrine (that's the purpose of the `--phpstan-other-stubs` option in the `generate-stubs` script).

When Concrete is installed, the permission keys come from the database, otherwise they are read from the CIF files in `concrete/config/install`.

## Notes

- When Concrete is installed, booting it connects to the database: the database server must be running to run PHPStan.
- The `phpstan.yml` GitHub workflow runs PHPStan on every push and pull request, using the same Composer scripts, with the `github` error format so that the errors are shown as annotations.
